## 2. 本次改动清单

### 2.1 问题原文

> 有逻辑bug，当我选择云端到云端，定位右边的路径，左边会同步修改到同样的位置，点击对比报相同路径比不出差异

现象可以完全复现，且**每一步都在用户预期之内、只有结果是错的**：

1. 把比对条左侧的来源也从「本地」切成「云端」—— 此时两侧都是云端；
2. 在右边的云端栏里换目录（点进某个子目录、或点面包屑上一级），定位到想比的那个目录；
3. 期望：右侧路径跟着走，左侧保持不动；
   实际：**左侧也被改成了同一个路径**；
4. 点「比对」，被拦下：**「两侧是同一个位置，比不出差异」**。

第 4 步的拦截本身是对的（同一个位置确实比不出差异），问题在于**用户根本没机会把左侧设成别的目录** ——
他每动一次右边，左边就被同步一次。

**这是 2.9.2 引入的回归。** 2.9.1 及之前不存在这个 bug，因为那时左侧只能选本地、右侧只能选云端，
两个输入框天然对应两个不同的浏览栏，永远不会撞车。2.9.2 允许两侧同源，
"两个输入框 ↔ 两个浏览栏"这个隐含的一一对应**第一次被打破**，而跟随逻辑仍然按旧假设取数。

### 2.2 根因：跟随逻辑按「来源类型」去取栏位路径

比对条有一条「跟随浏览位置」的机制：`loadLocal()` 与 `loadCloud()` 每次浏览结束都会调用
`autoFillCompareBar()`，把当前浏览到的目录回填进比对条（用户一旦手填过路径就停止自动覆盖）。
旧实现是这样取值的：

```js
// app/www/index.html（2.9.2）
$("cmpLocal").value = (state[cmpSide.left]  && state[cmpSide.left].path)  || "";
$("cmpCloud").value = (state[cmpSide.right] && state[cmpSide.right].path) || "";
```

读法是「**按这一侧声明的来源类型，去取对应那个浏览栏的当前目录**」。
`state` 里只有两份浏览状态：`state.local`（左栏，本地浏览器）与 `state.cloud`（右栏，云端浏览器）。

两侧都选云端时，`cmpSide.left` 与 `cmpSide.right` 都是 `"cloud"`，于是**两个输入框都去读
`state.cloud.path`** —— 同一个变量。任何一次云端浏览都会把两条路径写成同一个值。

这不是"同步做得太积极"，而是一个**信息不足**的问题：界面上只有一个云端浏览栏，
它无法同时表达两个不同的云端位置。旧代码没有承认这一点，而是让两个框都去抢这一个值。

### 2.3 修法：把两个浏览栏**唯一分配**给两个输入框

修复的核心是一条不变量：**一个浏览栏绝不服务两个输入框**。

分配分两轮，先到先得：

```js
function cmpPaneMap(){
  const out={left:null,right:null},taken={};
  // ① 栏位对得上的先占 —— 左框↔本地栏、右框↔云端栏（和两栏的排列一致）
  ["left","right"].forEach(w=>{
    const own=w==="left"?"local":"cloud";
    if(cmpSide[w]===own&&!taken[own]){out[w]=own;taken[own]=true;}
  });
  // ② 剩下的框再按自己的来源类型去领一个还没被占用的栏
  ["left","right"].forEach(w=>{
    if(out[w])return;
    const want=cmpSide[w];
    if(!taken[want]){out[w]=want;taken[want]=true;}
  });
  return out;
}
```

四种组合的结果，逐一交代：

| 左右来源 | 谁跟随哪个栏 | 说明 |
|---|---|---|
| 本地 ↔ 云端（默认） | 左框跟本地栏、右框跟云端栏 | **与 2.9.1 / 2.9.2 的操作体验逐字一致** |
| 云端 ↔ 云端 | **只有右框跟云端栏，左框不动** | 本次要修的场景；左框由用户自己填 |
| 本地 ↔ 本地 | 只有左框跟本地栏，右框不动 | 与上一行完全对称 |
| 云端 ↔ 本地 | 左框跟云端栏、右框跟本地栏 | 交叉跟随 —— 两个栏各有归属，一栏一框 |

`autoFillCompareBar()` 与「比对 ⇄」按钮用的 `syncCompareBar(true)` 都改成走这个分配：

```js
function autoFillCompareBar(){
  if(cmpBarAuto){
    const pane=cmpPaneMap();
    ["left","right"].forEach(w=>{
      if(!pane[w])return;                    // 没有对应栏的那一侧：浏览别人时不许动它
      const st=state[pane[w]];
      cmpInputOf(w).value=(st&&st.path)||"";
    });
  }
  ...
}
```

「云端↔云端时左侧保持不动」不是特判出来的，而是"这个栏已经被右侧占用了"的自然结果。

### 2.4 同源时不再预填出一个「注定报错」的路径

切来源时原本会做一件事：把该侧路径换成"该来源栏当前所在的目录"（因为换来源后旧路径多半不成立，
拿一串本地路径去比云端只会白报错）。但在两侧同源时，这个动作会**立刻填出一个和对面完全一样的值**，
用户还没动手，就已经处在一个"点比对必然报错"的状态里。

现在改为：**分得到栏才预填，分不到就留空**。

```js
cmpInputOf(which).value=cmpPaneOf(which)?(paneCompareRoot(side)||""):"";
```

留空是更诚实的表达 —— 那一侧确实还没有被指定，输入框的 placeholder 会提示格式。

### 2.5 报错要说清「改哪一边」

「两侧是同一个位置」这个拦截保留（它是对的），但补上两件事：

* **两个输入框都标红** —— 原来只弹一句提示，用户不知道该改左还是改右；
* 提示语补全动作：「两侧都是**云端**、且都指向 `/xxx` —— 同一个位置比不出差异，**请把其中一侧改到别的目录**」。

另外，两侧同源时比对条下方会常驻一行引导（原来是静态说明文字，现在按状态切换）：

> 两侧都选了 **云端**：下面只有**一个云端栏**，它只会带动 **右侧** 的路径。
> 另一侧请在上面**手动填写**要对比的目录 —— 两侧指向同一个位置是比不出差异的。

这行字解决的是"用户以为自己在浏览另一侧"的误解：他不是做错了什么，而是这个栏只能带动一侧。

### 2.6 旧存档里的同值会被自动纠正

被这个 bug 影响过的用户，关闭应用时那两条相同的路径会**存进界面状态并恢复回来** ——
升级后一打开就卡在"点比对就报错"的状态里，像是没修好。

所以恢复记忆值时加了一步去重：两侧同源、且两个框落到同一个位置时，把**没有对应浏览栏**的那一侧留空。

```js
function blankUnfollowedDup(){
  if(cmpSide.left!==cmpSide.right)return;
  const pane=cmpPaneMap();
  const loose=pane.left?"right":(pane.right?"left":null);
  if(!loose)return;
  if(cmpPathOf(loose)!==""&&cmpPathOf(loose)===cmpPathOf(OTHER_SIDE[loose])){
    cmpInputOf(loose).value="";
  }
}
```

只在"同源且同值"时动手，不动任何其它情况；用户自己填的两个不同目录不受影响。

### 2.7 为什么 2.9.2 的测试没抓到这个 bug —— 这段必须写下来

**上版有一条用例测了「云端↔云端」，而且是绿的。** 它是这样写的：

```js
await tapCmpSide(env, doc, "left", "cloud");     // 两侧都切成云端
doc.getElementById("cmpLocal").value = "/cloud-a";   // 直接给两个框赋值
doc.getElementById("cmpCloud").value = "/cloud-b";
await tapCompare(env, doc);                      // 断言提交了 /cloud-a 与 /cloud-b
```

它**直接给输入框赋值**，绕过了"浏览 → 跟随"这条路径 —— 而 bug 恰恰只在"同源 **且** 发生浏览"
这个组合下出现。两条断言覆盖了「协议层能表达两侧同源」，却漏掉了「界面上怎么把两侧设成不同的值」。

更糟的是另一条用例：`testCompareSideDefaultsAndSwitch` 里断言

```js
eq("左侧路径换成云端栏当前目录", doc.getElementById("cmpLocal").value, "/");
```

**这条断言把 bug 当成了规格**。它测的是"切到云端后左侧被填成了云端栏当前目录"，
而同源时那个"云端栏当前目录"本来就是跟对面同一个值 —— 断言在保护错误行为。本版已把它改写成
`eq("切到同源时不再预填出同款路径", ..., "")`。

两条教训，已固化进反向验证技能：

* **测试要沿"用户的动作序列"走，不要跳步**。直接赋 DOM 值 = 跳过了整个交互层，
  而 bug 常常正好住在被跳过的那一段里。
* **一条断言可能是"bug 快照"**。当修复需要改变一条既有断言的预期时，要停下来问：
  **它原本在保护什么？** 如果答案是"保护我正要删掉的行为"，那它就不是回归防线，而是 bug 的固化。

## 4. 刻意保持不变的行为

1. **默认组合不变**。不切任何开关时，左 = 本地、右 = 云端，两栏各跟各的栏 ——
   与 2.9.1 / 2.9.2 的操作体验**逐字一致**。
2. **后端一行未改**。`POST /api/compare` 的请求与响应结构、`/api/sync/copy`、
   云端异常的五种分类提示、`absPath`/`peerAbsPath`/`owner` 的回传，全部保持原样。
3. **本地侧的选择与比对逻辑不变**。白名单校验、深度收敛、父子归并、三组差异判定、
   `.ddpart` 永久排除，一行都没改。
4. **手填过的路径仍然不被自动覆盖**。`cmpBarAuto` 的语义没变：用户改过输入框之后，
   浏览位置就不再回填任何一个框。
5. **绝不自动删除任何文件**。「清除」必须用户显式点下且（批量的）二次确认之后才执行；
   「目录绑定备份」依旧只增不删。
6. **比对本身是纯只读的**。`POST /api/compare` 不改动任何一端的文件。
7. **两侧指向同一位置仍然被拒绝**，且**在发请求之前**就拒绝 —— 本版只是把提示做得可操作，
   没有放宽这条守卫。
8. **既有磁盘结构未改**：没有新增落盘文件，覆盖升级不丢任何配置与队列。

## 5. 已知边界与本次未做的事

- **同一类型的浏览栏只有一个，这是界面结构的硬约束**。所以「云端↔云端」时，
  只能靠"浏览定位一端 + 手填另一端"。本版做的是**把这个约束讲清楚并让它不再出错**，
  没有做"给云端再开一个浏览栏"这种界面改动 —— 那是一次真正的功能扩展，
  不该混在一个缺陷修复版里。
- **没有做「把另一侧设为当前栏位置」的快捷按钮**。它能让同源组合少一次手填，
  但属于新增交互，本版刻意不做。
- **比对只按大小，不比哈希**：两边字节数相同就判「一致」。
- **云端↔云端复制是"提交给服务端"**：同存储同步完成，跨存储由 OpenList 建后台任务，
  应用只回传任务 id 与已受理条数，**不跟踪后台任务的最终成败**。
- **差异清单不自动刷新**：搬完一项该行会摘掉，但在别处动过的文件需要重新点一次「比对」。
- **没有在真机上装过** —— 这是每次交付后的固定待办，落点是在飞牛应用中心 → 手动安装这个 fpk。
