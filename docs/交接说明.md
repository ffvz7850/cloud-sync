## 1. 30 秒上手

所有命令都在**工程根目录**（含 `manifest` 的那一层）执行。

```bash
# 1) 全部单元测试 + 前端断言（Python unittest + jsdom 真跑页面脚本）
python tests/run_all.py

# 2) 端到端冒烟：起真实 HTTP 服务 + 一个「真走 HTTP 的假 OpenList」，跑完整链路
python tests/smoke_e2e.py

# 3) 反向验证（变异测试）—— 证明测试「有能力发现回归」，先体检锚点（秒级）
python tools/mutcheck.py --anchors
python tools/mutcheck.py                 # 完整跑，约 10 分钟

# 4) 打包成 fpk
python tools/build_fpk.py --project .
```

环境要求：

- **Python 3.8+**（开发机用什么都行，NAS 上是飞牛的 `python3`）。用 `sys.executable` 跑测试，不需要额外配置。
- **Node.js**（仅前端测试需要，要能 `require('jsdom')`）。找不到 jsdom 时：

  ```bash
  npm i jsdom                                    # 任意目录
  DD_NODE_PATH=<那个目录>/node_modules python tests/run_all.py
  DD_NODE=/path/to/node python tests/run_all.py  # 找不到 node 时也可显式指定
  ```

- **fnpack**（飞牛官方打包 CLI）：已经放在 `tools/fnpack.exe`（Windows 版，3.8 MB）。
  其他平台去 <https://developer.fnnas.com/docs/cli/fnpack/> 下载后放进 `tools/`，
  或用 `--fnpack <路径>` 指定。查找顺序：`--fnpack` 参数 → `../_fnpack/fnpack.exe`
  → `tools/fnpack[.exe]` → `PATH`。

**本机起服务调试**（不装 NAS 也能看界面）：

```bash
python app/server/main.py --tcp 127.0.0.1:8380     # --tcp 的值是 <地址>:<端口>
# 浏览器打开 http://127.0.0.1:8380/
```

此时运行期数据落在工程下的 `_devdata/`（不碰真实环境），可以随便造。

## 3. 架构与关键设计

### 3.1 后端分层（从上到下，改哪层很清楚）

```
前端 index.html
   │  fetch("/api/...")  经飞牛网关 → Unix Socket
   ▼
main.py            起监听、加载队列
   ▼
http_api.py        路由 + 参数校验 + 错误分类 + 白名单 + 审计   ← 所有接口都在这
   ▼
verify.py          比对    upload_queue.py / download_queue.py   队列
bindings.py        绑定备份      │
   ▼                            ▼
openlist.py        OpenList 业务语义（登录、列目录、复制、删除、分片）
   ▼
httpclient.py      HTTP 传输（urllib 或 curl）    hasher.py  SHA-256
   ▼
config.py          路径与配置（飞牛的 TRIM_* 目录约定）
```

- **所有网络交互都收敛在 `openlist.py`**，出问题改这一处。
- **所有接口都在 `http_api.py` 的 `_ROUTES` 字典里**，加接口改这里（`tests/test_contract.py`
  会核对路由数与前端实际用到的路径）。
- `verify.py` 不关心某一侧是不是云 —— **两侧是对称的**，`{side, path}` 描述，
  每个条目回传**它自己那一侧**的绝对路径（`absPath` / `peerAbsPath`）。这是
  2.9.2 之后的设计，前端不再按「左=本地、右=云端」硬拼路径。

### 3.2 前端：单文件、无构建

`app/www/index.html` 里 HTML/CSS/JS 全内联，**没有打包器、没有压缩、没有框架**。
改完刷新页面即可（NAS 上装的是同一个文件）。代价是文件大（2700 行），
好处是「改一行立刻生效」「不需要 Node 工具链」。

- 接口基址在启动时用 `probeBase()` 探测（试 `""`、`/app/doubao-drive` 等），
  所以本地 TCP 调试与网关内嵌两种方式共用同一份代码。
- 界面状态分两层：`state`（会话内，如当前浏览路径、连接状态）与
  `uiState`（`localStorage` 持久化，如筛选记忆、草稿）。密码类**不落** `uiState`。

### 3.3 数据流：比对 → 传输 → 校验

这是应用的主线，也是改动最集中的地方：

```
选两侧目录 → POST /api/compare → verify.py 双向扫描（递归深度两边统一收敛）
   ▼ 四组：仅左侧有 / 仅右侧有 / 大小不一致 / 已同步（只读）
   ▼ split_diff() 做父子归并 —— 目录已列为差异项就不再单列子项
勾选 → 批量或单条：
   · 本地 ↔ 云端 → 进上传/下载队列（PUT/GET 流式、进度、指数退避重试、断点续传）
   · 云端 ↔ 云端 → OpenList 服务端复制（POST /api/sync/copy，按父目录分组，整组失败降级逐条）
   · 本地 ↔ 本地 → 本地复制（白名单校验 + 拒根目录 + 拒目标落在源内部）
传输完成 → 校验（比对云端大小）→ 一致才算成功
```

**队列是「百度网盘客户端」体验的核心**：任务持久化到 `upload_queue.json` /
`download_queue.json`，应用重启后未完成的自动恢复（分片断点续传，已传的分片不重传）。
下载队列**继承**上传队列 —— 持久化、退避、暂停/取消这些机制完全同构，只覆写
「入队打标记」和「执行任务（把 PUT 换成 GET）」两处。

**批量不是并发**：`h_sync_copy` 里按 `(src_dir, dst_dir)` 分组，**串行**发请求。
曾经因为逐条串行发几十次往返导致「点了很久没反应」，后来改成先返回、后台跑并给进度。

### 3.4 运行期文件落在哪

飞牛的目录约定（`config.py` 里统一解析，脱离飞牛时全部退到工程下 `_devdata/`）：

| 环境变量 | 实际位置 | 放什么 |
|---|---|---|
| `TRIM_APPDEST` | `/var/apps/doubao-drive/target` | 应用代码本身；`app.sock` 也在这 |
| `TRIM_PKGVAR` | `/var/apps/doubao-drive/var` | `config.json`、`credentials.json`、`upload_queue.json`、`download_queue.json`、`audit.log.jsonl`、`info.log`、`app.pid` |
| `TRIM_PKGETC` | `/var/apps/doubao-drive/etc` | `settings.conf`（`KEY=VALUE` 纯文本，**值里可能带空格，不能用 `source` 加载**） |
| `TRIM_PKGTMP` | `/var/apps/doubao-drive/tmp` | 临时文件 |

**配置优先级**：`settings.conf` > 环境变量 > 代码默认值。界面上改的写进 `config.json`。

`TRIM_DATA_ACCESSIBLE_PATHS` 是**本地浏览与操作的白名单**（路径列表，分隔符走
`os.pathsep`）。所有本地读写都受它约束 —— 见 §4.5。

## 4. 开发铁律

**这一节是血泪换来的，违反了下场是「装上去起不来、还没日志」。**

### 4.1 飞牛的 Python 是裁剪构建 —— 禁止顶层硬导入「靠 C 扩展的标准库」

实测飞牛自带 `python312` **缺 `_lzma`**，`hashlib`/`ssl` 这类也**不保证有**。
所以 `app/server/` 里**任何模块都不许在顶层硬导入**依赖 C 扩展的标准库：

> `lzma` `bz2` `gzip` `zlib` `zipfile` `tarfile` `sqlite3` `hashlib` `ssl` `ctypes`

正确做法是**能力探测 + 降级**，本工程已有两个先例可照抄：

| 模块 | 探测 | 降级 |
|---|---|---|
| `hasher.py` | 真算一次 SHA-256（**不是**只看能不能 import —— 有些裁剪构建能 import、调用时才炸） | 纯 Python SHA-256 实现 |
| `httpclient.py` | 探测 `urllib` + `ssl` 能否真的发 HTTPS | 退到系统 `curl` 子进程 |

顶层 import 白名单（当前实际在用，都安全）：
`os` `sys` `time` `json` `copy` `threading` `tempfile` `shutil` `struct` `uuid`
`fnmatch` `subprocess` `argparse` `signal` `socketserver` `stat`
`http.server` `urllib.parse`。

> 另注：`httpclient.py` 里有个性能教训 —— **内网 `http://` 不需要 ssl**，
> 早期版本把「ssl 缺失」当成「所有请求都要走 curl」，于是每发一次请求 fork 一个
> curl 子进程；云端扫描是「每目录一次请求」，几百个目录就是几百次 fork。

### 4.2 `cmd/*` 必须 LF 换行、无 BOM、有可执行位

- **CRLF** → NAS 上直接 `bad interpreter: No such file or directory`。
- **UTF-8 BOM** → 同样起不来。
- **没有可执行位** → `Permission denied`，应用永远起不来，`status` 一直返回 1，**日志里什么都没有**。

第三条特别阴：`fnpack` 在 **Windows 上打出来的 `cmd/*` 权限是 0666**。
所以 `tools/build_fpk.py` 在打包后**补一刀**（目录与 `cmd/*` 设 755、其余 644），
并在自检里核对 `cmd/main` 确有可执行位。**别绕过这一步。**

### 4.3 每次改动都要迭代版本号，且只加不覆盖

用户明确要求过。改动必须动**三处**（少一处就会出现「装的版本和测的版本对不上」）：

1. `app/server/config.py` 的 `APP_VERSION`
2. `manifest` 的 `version` **和** `changelog`（changelog 用 `<br>` 分隔、面向用户写人话）
3. `README.md` 的版本段 + 根目录新写一份 `doubao-drive-<版本>-说明.md`，
   并把**上一版**的说明 `cp` 进 `docs/历史说明-<上一版>.md`

`tests/` 里**没有**硬编码版本号（有意如此），所以升版不会碰测试。

### 4.4 交付只给 fpk（除非用户明确要源码）

用户的历史要求是「以后只输出 fpk 文件即可」。源码包只在用户明确要求时才出。

### 4.5 不可逆操作必须有白名单 + 审计

删除、覆盖这类操作（云端 `fs/remove`、本地删除、本地复制）必须：

1. 先做**全部校验**（白名单越界、根目录本身、源即目标、目标落在源内部），
   **判完再动文件系统** —— 否则「目标是源的子目录」这种误操作一旦先 `makedirs`，
   用户凭空多出空文件夹还得自己删；
2. 界面二次确认；
3. 写 `audit.log.jsonl`（追加一行，含时间、操作、路径、结果）。

白名单来自 `TRIM_DATA_ACCESSIBLE_PATHS`，校验要 `os.path.normcase` 归一化后比较
（Windows 路径大小写不敏感，网络盘挂载点尤其容易绕过去）。

### 4.6 `.ddpart` 临时文件永久排除

下载先写 `<目标>.ddpart` 再 `os.replace` 到目标。这个后缀在所有扫描、比对、
上传入队里**永久排除**（`verify.ALWAYS_EXCLUDES` + `effective_excludes()`），
否则半截文件会被当成真实文件参与比对和传输。

### 4.7 测试的 teardown 不要用 `shutil.rmtree`

本环境（沙箱化 Windows）**删文件极慢，约 3 秒/次**。测试清理用 `rmtree` 会让
一个本该几秒的用例跑几十秒。做法是：临时目录用够就好，不留清理代码；
测试数据目录按 PID 隔离（`_bootstrap.py` 已经这么做了）。

## 5. 测试体系

| 前端断言 | 同上（自动含 jsdom） | **499** 项（`test_ui.js` 413 + `test_bindings_ui.js` 86） | 真的用 jsdom 跑页面脚本，断言 DOM 与请求载荷 |

| `test_bindings.py` | 绑定备份的状态机、增量扫描、任务查询 |

### 5.2 前端测试怎么驱动（改 UI 前先看这里）

`test_ui.js` 用 jsdom 加载 `index.html`，**真跑页面里的脚本**，并塞一个假后端
（拦 `fetch`）。要点：

- `makeWindow()` 造环境；`makeBackend()` 造假后端，返回体形状要与 `http_api.py` 一致；
- `flush()` 等一轮微任务/宏任务，让 `await` 链跑完；
- 用户级动作要用辅助函数**沿真实动作序列**执行（如 `tapCmpSide` → 点切换按钮 →
  `tapCompare` → 点比对），**不要直接改 DOM 值再断言**。

> **为什么强调「不要跳步」**：曾经有一条「云端↔云端」用例是绿的 —— 它直接给两个
> 输入框赋值再点比对，**跳过了「浏览 → 路径跟随」这段，而 bug 正好住在那一段里**。
> 测试要沿用户的动作序列真做一遍，否则它保护的是一个不存在的流程。

### 5.3 反向验证（变异测试）—— 「测试全绿不是证据」

做法：把关键分支逐条改坏（`MUTATIONS` 列表），断言对应测试**必须变红**。
如果某条变异之后测试**仍然全绿**，说明那条断言是空的（假绿），要补断言。

```bash
python tools/mutcheck.py --anchors        # 先体检锚点（秒级），重构后必跑
python tools/mutcheck.py                  # 全部跑，约 10 分钟
python tools/mutcheck.py --only 关键词     # 只跑某几条（调试新加的变异）
```

四个必须知道的机制：

1. **锚点是代码的文本快照**（`(说明, 文件, 原文, 替换成, 测试命令)`）。重构会让锚点
   悄悄失效 —— 表现为安静的 `SKIP`（不变红、不中止、汇总行仍报「全部变红」）。
   **整段函数被重写时，锚点要「改指向」而不是删掉**，否则是覆盖面的盲区。
2. **备份与中断守卫**：开跑前把所有目标文件备份到系统临时目录
   （`DD_MUTBAK` 可覆盖），跑完打一个**成功戳**。「备份比戳新」= 上一轮没跑完，
   下次启动自动逐字节还原。**为什么用打戳而不是删备份**：删除在部分受限环境会
   被拦掉，于是一个已经全绿的 10 分钟长跑最后以非 0 退出、汇总行也不打印，
   看起来像失败。**为什么备份不能放工程内**：万一中断把变异态留在源码里，
   那份坏文件会被打进包。
3. **`--only` 模式只跑匹配的变异**，加新变异时用它快速验证，不必等 10 分钟。
4. **运行期间不要改代码**：变异脚本会临时改文件再还原，此时编辑会造成互相踩。

**判据**：*一条断言的强度 = 它对应的那处代码被删后它变不变红。*
加断言时要顺手问一句「删掉被测那行，它会红吗」—— 不会红就说明还是假绿。

## 6. 改代码的标准流程

```
1. 定位            改哪一层？接口层 http_api.py，业务 openlist.py/verify.py，界面 index.html
2. 改代码          遵守 §4 的铁律（尤其 4.1 的裁剪 Python）
3. 补测试          改后端 → test_*.py；改界面 → test_ui.js（沿真实动作序列）
4. 跑全量          python tests/run_all.py        必须全绿
5. 跑冒烟          python tests/smoke_e2e.py      改了接口/传输必跑
6. 反向验证        python tools/mutcheck.py --anchors  然后 python tools/mutcheck.py
7. 升版本          config.py + manifest（version 与 changelog）+ README + 新说明文档
8. 打包            python tools/build_fpk.py --project .
9. 收口三核        包内文件与工程源码逐字节一致 / 包内版本号正确 / 产物 md5 记进说明文档
```

**第 9 步的「收口三核」不是形式主义**：曾经出现过「测的是 A、打出去的是 B」
（打包暂存目录里留着旧文件），以及「文档里写的 md5 与实际产物不一致」。
做法是打包后**从 fpk 解包**（fpk 是 tar.gz 套 app.tgz），对**包内代码**再跑一次冒烟。

```bash
tar -xzf dist/doubao-drive.fpk -C /tmp/chk && tar -xzf /tmp/chk/app.tgz -C /tmp/chk
python tests/smoke_e2e.py /tmp/chk/app      # 对包内代码跑冒烟
```

> ⚠️ **一个反直觉的点：不要用 md5 判断「重新打的包」和「交付的包」是否等价。**
> `fnpack build` 会往 `manifest` 里**注入一行 `checksum`**（由包内容与打包时刻算出）。
> 于是同一份源码打两次，md5 必然不同、字节数也会差几个 —— 这**不是**打包出错。
> 等价性要按**内容**判：解开两个包逐条目比对，除 `manifest` 的 `checksum` 行
> 与各条目的时间戳外应当完全一致。
> 所以「包内文件与工程源码逐字节一致」这条核对，要在**打包暂存目录 `build/fpk`**
> 上做（那时 fnpack 还没注入 checksum），而不是直接从 fpk 里解出来的那份。

## 9. 常见坑速查

| 症状 | 原因 | 处置 |
|---|---|---|
| 自己按文档打包，md5 与说明文档里写的不一样 | `fnpack build` 会往 `manifest` 注入一行 `checksum`（含打包时刻） | **正常**。按内容比对而不是 md5；文档里的 md5 只是「那一份交付物」的指纹 |
| 应用装上但起不来，`status` 返回 1，日志全空 | `cmd/*` 没有可执行位（Windows 上 fnpack 打出来是 0666） | 用 `tools/build_fpk.py` 打包（它补权限），别直接调 fnpack |
| NAS 上 `bad interpreter: No such file or directory` | `cmd/*` 是 CRLF 或带 BOM | 转 LF、去 BOM（自检会拦） |
| 后端启动报 `ModuleNotFoundError: _lzma` / 调用某标准库时炸 | 顶层硬导入了依赖 C 扩展的标准库 | 改成能力探测 + 降级，见 §4.1 |
| HTTPS 请求全失败 | 裁剪 Python 没有 `ssl` 且系统没有 `curl` | `httpclient` 会报「ssl 与 curl 都不可用」；装上 curl 或换 Python |
| 前端测试报 `Cannot find module 'jsdom'` | 没有 jsdom 或路径没指对 | `DD_NODE_PATH` 指到含 `node_modules` 的目录，见 §1 |
| 打包报「缺少 wizard/」 | 空目录没被打进去 | 用 `tools/pack_src.py`，它会显式写空目录条目 |
| 打包报 `not valid due to JSON format...` | 往空 `wizard/` 里放了 install/uninstall 文件 | 保持 `wizard/` 为空目录 |
| 变异脚本跑完有文件被改坏 | 上一轮被中断留下残留 | 重跑一次 `tools/mutcheck.py`（启动自动还原）；确认源码后再继续 |
| 变异全跑完却报「锚点失效」 | 重构让某条锚点的文本快照对不上了 | `--anchors` 定位，改指向而不是删条目 |
| `curl` 每个请求都 fork 一个进程、扫描很慢 | ssl 探测把内网 http 也判成要走 curl | 见 `httpclient.py` 的 `_probe_plain_urllib()` |
