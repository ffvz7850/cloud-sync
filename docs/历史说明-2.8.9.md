## 2. 本次改动清单

> **只想看本轮的改动？** 直接跳 **2.7 节**（一键上传提速：提交的请求数降 45%）。
> 2.6 节是 2.8.8 的交互优化（实时进度 + 禁用重复点击），2.5 节是 2.8.7 的修复（绑定任务传完就从传输列表消失），
> 2.4 节是 2.8.6 的修复（一键上传没反应），2.1~2.3 节是 2.8.5 的 7 处性能优化 —— 本版**一并承接**，为完整性保留在这里。

本版 = **1 组提交提速 + 1 处放大器修复**（2.7 节）+ **2.8.8 的交互优化**（2.6 节）+ **2.8.7 的修复**（2.5 节）+ **2.8.6 的修复**（2.4 节）+ **7 处性能放大源的消除**（2.1~2.3 节，来自 2.8.5）。

先说优化部分：共 **7 处放大源**。慢不是一个原因造成的，而是好几个「每目录一次」「每文件一次」的串行开销叠在一起：

```
扫描一个 300 目录 / 5000 文件的云端库
  ├─ 300 次 HTTP 请求        ← 每目录一次，原来是串行的     ① 并发
  │    └─ 其中大目录还要翻页  ← 每 1000 项一次              ⑤ 自适应分页
  ├─ 每次请求都重读 2~4 个磁盘文件（凭据/配置/设置）       ④ 文件读取缓存
  ├─ 缺 _ssl 的机器上每次请求 fork 一个 curl 子进程         ③ 按协议选后端
  └─ 绑定比对时还要逐文件 stat 云端  ← 5000 文件 × N 目标   ② 按父目录批量列
```

每条给：**现象 → 根因 → 修法 → 效果**。

### 2.1 云端扫描：从「一目录一往返」到「同层并发」

#### ① 云端目录扫描是纯串行的，目录一多就卡成一条直线

- **现象**：对比页 / 绑定扫描在目录较多的库上进度条一格一格挪，几百个目录要等很久；换成 `http://` 内网地址也没变快。
- **根因**：`scan_cloud()` 用的是一个 `while` 循环加栈，**一次只列一个目录、等它返回再处理下一个**。而云端扫描的成本几乎全在网络往返上（每个目录 = 一次 `/api/fs/list`）。D 个目录就是 D 次串行 RTT，和带宽没关系，纯粹在等。
- **修法**：改成**分层 BFS + 同层并发**：
  - 同一层的所有目录用固定 N 个工作线程一起列（默认 8，可在设置里按 1~32 调）；
  - 层与层之间仍然串行 —— 因为要拿到上一层的结果才知道下一层有哪些目录。
  - 自写了 `map_concurrent(fn, items, workers)`（游标 + 锁的固定线程池，**结果按输入顺序返回**）。刻意不用 `concurrent.futures`：飞牛的裁剪版 python 不一定编入了它 import 时会拖进来的 C 扩展，项目铁律是「依赖 C 扩展的标准库一律不做顶层硬导入」，所以只用 `threading`。
- **效果**：请求总数不变，但**等待时间从「D 次往返」压到大约「层数 × 每层轮数」**。目录多、层级浅的库提升最明显（理论极限接近 8 倍）；层级很深的库提升较小，但绝不会变慢。

#### ② 绑定比对：每文件 × 每目标一次云端 stat → 按父目录批量列一次

- **现象**：绑定扫描 5000 个文件、2 个目标目录时，扫描要跑很久，日志里能看出请求一个接一个。
- **根因**：快照模式下，源文件指纹没变但需要核对时，代码对**每个文件**分别调一次云端的 `stat`（`/api/fs/get`）。5000 文件 × 2 目标 = **1 万次请求**，全部是单文件查询，而同目录的兄弟文件其实一次列表就能一起拿到。
- **修法**：新增 `CloudEntryLookup`，改为**按父目录批量查**：
  - 收集所有需要核对的文件，按父目录去重；
  - 每个父目录只发一次 `/api/fs/list`，把直接子项建成一张表；
  - 之后每个文件查内存表即可。
- **效果**：5000 文件 × 2 目标从 **1 万次请求降到个位数**（按去重后的父目录数计）。这是本次单点收益最大的一条。

### 2.2 每个请求都在重复做同一件事

#### ③ 缺 `_ssl` 的机器上，连内网 `http://` 请求都要 fork 一个 curl 子进程

- **现象**：明明 OpenList 就在内网、走的是 `http://`，扫描却一边慢一边看起来「很吃 CPU」。
- **根因**：传输后端的选择函数 `detect_backend()` 回答的其实是**「能不能走 HTTPS」**。飞牛的裁剪版 `python312` 常常缺 `_ssl`，于是它返回「走 curl」。可这段判断是在**每个请求**上做的 —— 结果**内网 http 请求也被判成要走 curl**，每发一次请求就 `fork` 一个 curl 子进程。云端扫描是每目录一次请求，几百个目录 = 几百次进程创建。
- **修法**：新增 `pick_backend(url)`：**先看 URL 的协议**。`http://` 根本不需要 ssl，一律走 urllib；只有 `https://` 且 ssl 确实不可用时，才真的需要 curl。同时把 urllib 的 opener 复用起来（原来每次请求都 `build_opener`），并显式挂上空的 `ProxyHandler` 绕开系统代理劫持。
- **效果**：内网 http 场景下**彻底消除每请求一次的进程创建**；opener 复用到目前省下每个请求一次的构造开销。

#### ④ 每个 HTTP 请求都要重读 2~4 次磁盘上的配置文件

- **现象**：请求量一大，磁盘 IO 悄悄成为瓶颈；NAS 上数据目录在机械盘或网络卷时更明显。
- **根因**：`_raw_request()` 里先取 `self.base_url()`（一次读凭据文件），再取 `self.store.token()`（又一次读同一个文件）；config、settings 也各有各的读法。**一个请求里同一个文件被反复读**。
- **修法**：
  - `config.py` 加一层**按 mtime 失效的读取缓存**：`read_cached_json()` / `read_cached_lines()`，缓存键是 `(st_mtime_ns, st_size)`，文件没被改过就直接返回内存里的解析结果（返回深拷贝，避免调用方改到缓存）；写入路径（`atomic_write_json` / `atomic_write_text`）**主动失效**对应条目。
  - `_raw_request()` 改成**只读一次凭据文件**，base 与 token 都从这一份里取。
- **效果**：稳定态下这些文件从「每请求读 2~4 次」降到 **0 次**（mtime 没变就不读）。

### 2.3 一键上传与列表页

#### ⑤ 大目录还在「每 1000 项翻一页」——现在第一页就能要全

- **现象**：目录里项目特别多（几千上万）时，即使别的都优化了，光翻页就要好几次往返。
- **根因**：`list_all()` 固定每页 1000 项硬翻：一个 8000 项的目录要 **8 次往返**。
- **修法**：**自适应分页**。第一页返回里就带着 `total`，发现「这个目录比一页大」时，直接把 `per_page` 提到 `total` 一次要全；只尝试一次（`adapted`），失败就退回普通翻页。
  - **安全细节（关键）**：页码**只按实际返回的条数推进**，不按请求的 `per_page` 推进。因为服务端可能把 `per_page` 夹到它自己的上限 —— 如果按请求值推进页码，中间那些条目会被**跳过**，而漏掉的条目会被误判成「云端没有」从而重复上传。按实际条数推进就绝不会漏。
- **效果**：8000 项目录从 **8 次往返降到 2 次**；服务端不理会 `per_page` 时自动退回原路径，**结果依旧完整**，只是慢一点。

#### ⑥ 一键上传：每个文件被 stat 三次

- **现象**：点「一键上传」大目录后按钮像"没反应"，要等一会儿才开始动。
- **根因**：入队前用 `os.walk` 展开目录，再对每个文件单独 `isfile()`（一次 stat）+ `getsize()`（又一次 stat），叠加 `walk` 内部的开销 —— **每个文件 3 次 stat**。5000 文件就是 1.5 万次系统调用。
- **修法**：新增 `expand_local_dir()`，改用 `os.scandir()` 的 `DirEntry`：
  - `entry.is_dir(follow_symlinks=False)` 直接吃 `d_type`（Unix 上免 stat）；
  - 一次 `os.stat()` 同时拿到「是不是普通文件」（`S_ISREG`）和大小；
  - 顺手过滤设备 / FIFO 这类非普通文件，符号链接**跟随**（与原来的 `os.walk + isfile` 语义一致）。
  - 队列的 `add()` 也支持传入**预计算好的 size**，不再自己 `getsize`；没传时才回退去 stat（保持对旧调用方的兼容）。
- **效果**：每文件 **3 次 stat 降到 1 次**；「点了没反应」的等待明显缩短。

#### ⑦ 列表页每 2 秒重建整张表，哪怕数据一个字节都没变

- **现象**：任务多的时候界面发飘、滚动卡；即使队列是空的，后台也一直在轮询。
- **根因**：两件事叠在一起：
  - `loadTasks()` 每轮都无条件 `renderQueue()` —— **整表 DOM 重建**，几百行时每次都要重排，肉眼可见地卡；
  - 轮询间隔固定 2 秒，**队列空闲时也在按这个频率问**。而空闲时后端本身没什么可报的。
- **修法**：
  - 给响应算一个**指纹**（`queueSig`：暂停标志 + 每任务的 id / 状态 / 已传字节 / 重试时间 / 取消中标志 / 错误信息）。指纹没变就**不重绘**，DOM 原样保留。
  - 轮询间隔**自适应**：有活跃任务时 2 秒，队列空闲时降到 8 秒（`syncTaskInterval()` 在变化时才重启定时器）。
- **效果**：数据没变时**零重绘**（滚动、交互不再被重排打断）；空闲时对后端的轮询频率**降到 1/4**。

### 2.4 绑定备份：选中文件夹点「一键上传」没有任何反应

这是本版追加修复的一个**功能性 bug**（不只是慢），现象与 2.8.4 说明里承诺的行为直接冲突。

- **现象**：在「绑定备份」里展开某个绑定，选中其中**一个文件夹**（或整目录）点「一键上传」——
  - 界面上**没有任何反应**：既没有提示，卡片也没变化；
  - 传输列表里**看不到这个文件夹**；
  - 但去 OpenList 那边看，**确实有内容正在被复制**。
- **根因**：提交确实成功了（这一步有测试钉住），问题出在**提交后紧接着的那次状态同步**。
  绑定上传走的是 OpenList 的**服务端复制**（`/api/fs/copy`），复制是异步的：提交后返回一个任务，但
  - 该任务此刻可能还**不在** OpenList 的「进行中任务」列表里（端点轮询窗口 / 任务 id 不同源），
  - 同时云端目标目录里**文件也还没落地**。
  旧逻辑在这种情况下会**立刻**把该文件判回「缺失」：既然判成缺失，就不再属于「待处理/进行中」集合，
  于是它**从传输列表里消失**、绑定卡片上的计数又变回「缺失」——前后端都表现为「点了没反应」，
  而 OpenList 那边其实正在老老实实地复制。
- **修法**：把这三种「暂时说不清」的状态统一收进 **30 分钟宽限期**（`QUEUED_STALE_SECONDS`）：
  1. 复制任务一时查不到 → **保持「排队中/上传中」**，不再立刻下结论；超过宽限期才判失败并写明原因；
  2. 复制任务已结束但云端暂时读不到 → 同样先给宽限期等它落地，**只有云端核对成功且大小一致才转「已同步」**；
  3. 收口原则不变：**绝不因为「查不到」就谎报成功**，只在证据确凿时报成功。
- **顺带修掉的三处「静默」**（正是它们让这个 bug 看起来像「什么都没发生」）：
  - `GET /api/upload/list` 原来用 `except Exception: pass` 吞掉绑定数据读取失败 → 绑定任务整批消失却毫无提示。现在改为**记日志 + 把失败原因回传前端**，前端弹出可见提示；连续刷新失败也会提示。
  - 传输列表里给**绑定任务**误渲染了「取消」按钮（打向 `/api/upload/cancel`，绑定任务没有本地队列，必然 404 且被静默）→ 改为「**查看绑定**」，点击直接跳到对应绑定卡片。
  - 一键上传提交后**立即刷新**传输列表，不再等下一个轮询周期才看到。
- **同批复核的性能项**：绑定状态同步、传输列表、增量扫描三条热路径都改为**按父目录批量查询**（不再逐文件 `stat`）；单文件夹上传的路径匹配从线性查找改为**集合查找**（大文件夹不再卡）。这两项在 2.1② 已量化，此处确保修复没有把优化退回去。

### 2.5 绑定任务传完后从传输列表「消失」，而不是显示「已完成」

这是 2.8.7 修的 bug，紧接 2.4。

- **现象**：在绑定备份里上传一个文件夹，**传的过程中**传输列表里能看到它们（排队中 / 上传中），但**一旦传完，这些任务就从传输列表里消失了** —— 点「已完成」筛选也是空的。而本地上传队列的任务传完后是**留在列表里显示「已完成」**的，两边表现不一致，用户会以为「传完了怎么什么都没留下 / 到底成功没有」。
- **根因**：绑定文件复制完成后，状态从 `queued` / `uploading` 变成 `uploaded`（云端已有）。而传输列表的过滤条件是「只收进行中与失败」：

  ```python
  if st not in (ST_QUEUED, ST_UPLOADING, ST_FAILED):
      continue
  ```

  于是完成的那一刻，它**同时**从「进行中」集合里退出、又不满足「已完成」的收录条件 —— 在列表里凭空消失。更隐蔽的是紧挨着的下一行 `if not jobs: return []`：一旦没有进行中的文件就直接返回空列表，连收集的机会都没有。这一行是修 2.5 时最容易漏掉的地方（第一遍改动就是被它挡住的）。

- **修法**：
  1. 给完成时刻打上时间戳（`doneAt`），传输列表额外收录「**本绑定上传过、且仍在保留窗口内（10 分钟）**」的已完成文件，状态映射为 `done`；
  2. 「刚传完」与「云端本来就有」用**有没有上传痕迹**区分 —— `doneAt` / `queuedAt` 都没有的 `uploaded`，只是扫描时就已同步的文件，不该混进传输列表；
  3. 去掉 `if not jobs: return []` 这个提前返回（没有进行中的文件时，仍要把刚完成的收进来），同时保留「没有进行中就不去拉任务列表、不批量核对云端」的性能好处；
  4. 一次上传几千个文件时，已完成最多显示最近 **500** 条，保证列表还能用；
  5. 顺序上把「已完成」放前面、进行中放后面 —— 界面会把整个列表倒序渲染（最新的在最上），这样反转之后**进行中恰好排在最上面**，已完成落在下方。
- **为什么不直接把状态改成持久标记**：绑定文件的状态是扫描结果的一部分，不能为了列表好看去改它（动了会导致下次扫描重复判缺失、重复上传）。用时间窗口还有一个好处：重新扫描会把已同步的文件移出待处理列表，传输列表自然归零，不需要额外清理逻辑。

### 2.6 一键上传：从「点了没反应」到「过程可见、重复点击无效」

- **现象**：点「一键上传」后很长时间界面没有任何反应，要等十几秒才提示「已加入 N 个上传任务」；等待期间因为得不到反馈，会**反复点击**。而云端（OpenList）那边其实已经在复制了。
- **根因（两件事叠在一起）**：

  **其一，提交本身就慢。** 点一次「一键上传」不是一瞬间的动作：`upload_files` 按「源目录 + 目标目录」把待传文件分组（同一子目录的文件合成一组，一次 `fs/copy` 提交多个名字），然后**逐组串行**发两次请求 —— 一次 `ensure_dir`（建目录）、一次 `fs/copy`。选一个含 30 个子目录的文件夹就是 **60 次串行网络往返**，十几秒起步。这正是「要等较久」的绝对值来源（2.1~2.3 的优化都落在扫描与绑定比对上，没覆盖这条提交路径）。

  **其二，等待期间零反馈。** 前端 `doUpload` 在 `await api("/api/bindings/upload", ...)` 期间**不改变任何界面状态**：按钮不变、不禁用、没有 loading，只有一句 `toast` —— 而那是在请求**返回之后**才弹的。于是用户看到的是一幅静止画面，自然会以为没点上，然后反复点击（后端当时也没有幂等保护，每次点击都是一份真实的重复复制请求）。

- **修法**（对应三条诉求）：

  1. **点下去立刻有反应**：`doUpload` 开头同步把按钮切成「提交中」（禁用 + 转圈），并在卡片顶部插入状态条 —— 这一切发生在请求发出**之前**。没有状态条时**就地插入**，不走整卡重绘（重绘会把用户展开的目录树收起、滚动位置打回顶部，那正是「点一下界面乱跳」的来源）。
  2. **实时展示进度与处理状态**：后端为每次提交维护一份**内存态**进度（`phase` / `done` / `total` / `files` / `submitted` / `failed` / `message` / 耗时），前端每 500ms 拉一次并就地更新：

     ```
     正在收集待上传文件…  →  正在提交到云端（4/10 个目录）…  →  云端复制中：xxx.mkv 45%  →  已提交 120 个文件（耗时 9 秒）
     ```

     提交阶段的进度查询走「轻量模式」（`?submit=1`）：**纯读内存、不打云端**，所以能高频轮询。提交完成后接力显示云端复制进度（原来这里每 2 秒弹一条 toast「复制中：xxx 45%」，连续几十条比没有更烦，现在改成画进同一条状态条）。
  3. **操作进行中禁用重复点击**：该绑定的「一键上传 / 上传 / 上传选中 / 全部上传 / 扫描」全部锁住（「扫描」也要锁 —— 它会重写各目标状态，与正在提交的那批文件抢同一份数据）。服务端另有一道**幂等闸门**：同一绑定正在提交时再次请求会被明确拒绝（「该绑定正在提交上传，请稍候再试」）。因为前端的按钮禁用只是体验层 —— 双击、两个标签页同时点、提交期间又触发一次自动扫描上传，都会绕过它。刷新页面后按钮仍从后端的 `submitting` 标记恢复禁用态，否则一刷新防护就没了。
  4. **顺带让提交变快**：每个目录组的两组请求原本串行，现在按设置里的「扫描并发数」**并发提交**（同一个「向 OpenList 发几路请求」的旋钮，远端或限流时调小即可，不必再多一个配置项让人犹豫该动哪个）。并发与串行交出去的文件集合**逐项一致**，测试两种路数都跑。

- **顺带修掉一个一直存在的接口缺陷**：`/api/bindings/progress` 是全项目**唯一**一处没对查询参数取首值的地方（其他都写 `_arg(query, "id")`，只有它写了 `(query or {}).get("id")`）。而 `parse_qs` 解析出来的值是**数组**（`{"id": ["bd_xxx"]}`），于是它拿着 `["bd_xxx"]` 去查绑定，永远查不到，恒定返回 `progress: null`。**结果是前端那个 2 秒一次的「云端复制进度」轮询从未真正生效过** —— 这正是「从来没见过复制进度」的原因。现在按 id 能正常命中，并加了端到端（真 HTTP）断言钉住它。

- **为什么进度条的分母是「目录组数」而不是「文件数」**：用户等待的正是那几十次网络往返。按文件数画，会在「一组里有 100 个文件」时制造「显示 99% 却还要等很久」的假象。分母口径由后端算好（`percent`）再交给前端，两边不用各自猜。

### 2.7 一键上传提速：不再对同一批云端目录反复发请求

**现象**：点「一键上传」后要等较久才提交完，感觉比在 OpenList 网页上手动复制同一个文件夹慢得多。

**先把「谁慢」分清楚。** 用假客户端（每个动作都记一次请求）实测提交 120 个文件、分属 30 个子目录：

| | copy | 目录查询 | 目录创建 | 合计 |
|---|---|---|---|---|
| 在 OpenList 网页手动复制同一文件夹 | 1 | 0 | 0 | **1** |
| 本应用（2.8.8） | 30 | 90 | 36 | **156** |
| 本应用（2.8.9） | 30 | 36 | 36 | **102** |

复制本身只占 30 次，剩下 **126 次全是软件自己的开销** —— 「感觉是软件慢」这个直觉是对的。

**根因一：创建目录时对路径的每一级都查一次，而且并发之间不共享结果。**

`ensure_dir("/备份/相册/2024")` 会依次 `fs/get` 三次：`/备份`、`/备份/相册`、`/备份/相册/2024`。
一次提交有 30 个子目录 → 90 次查询，而其中**唯一路径只有 36 个，54 次（60%）是重复的父级**。
更糟的是 8 路并发 worker 各自跑这一套，谁也不看别人的结果。

**根因二：并发各自创建同一批目录。** 36 个唯一目录被 `mkdir` 了 57 次。

**修法**：一次提交内共享一份「已确认存在的目录」缓存（`openlist.DirCache`，线程安全）：

- 每级都先查缓存 —— **已确认存在的目录，后面的 worker 一个请求都不发**；
- 每个路径各自加锁，同一目录不会被并发重复创建；
- 加锁顺序恒定由浅到深、每级用完立刻释放（不是嵌套持锁），两个 worker 不可能各持一把锁互等。

**根因三（放大器）：提交进行中，传输列表还在同步轰炸云端。**

传输列表每 2 秒轮询一次，会被「进行中」的文件触发去列云端目录 —— 30 个子目录就是 **30 次 `fs/list`**；
而这些请求**必然是空的**（复制刚提交、文件还没落地），却和正在提交的请求抢同一个 OpenList。
现在提交进行中直接跳过该绑定的云端核对（列表照常渲染，用户仍看得到它正在传）。

**效果**（同一套量化脚本；「目录已存在」= 用户日常）：

| 场景 | 2.8.8 | 2.8.9 | |
|---|---|---|---|
| 再次提交（目录已存在） | 120 次 | **66 次** | −45% |
| 首次提交（目录要新建） | 156 次 | **102 次** | −35% |
| 重复的目录查询 | 54 次 | **0 次** | 归零 |
| 重复的目录创建 | 21 次 | **0 次** | 归零 |

**语义完全没变**：目录不存在才建、路径被同名文件占住仍如实报错（只是不再重复问同一件事）；
不传缓存的调用点（上传队列、建目录接口）行为照旧。这几条都有测试钉住。

**为什么不再进一步**：剩下的 36 次目录查询是「确认目标目录存在」的下限。再省就得靠**跨请求**的长期缓存 ——
那是一份会过期、会与 OpenList 实际状态脱节的假设（用户随时可能在 OpenList 那边删掉目录）。
用一个「快一点、但可能把文件复制到不存在的目录上」的实现去换这点收益，不划算。
**宁可 66 次都问对，也不要 30 次问错。**

## 4. 刻意保持不变的行为

做性能优化时最容易顺手把语义"优化"掉。以下这些**故意没动**，并且**每一条都有测试钉住**：

1. **扫描失败绝不吞掉**：某个目录列不出来时照样 `raise`，**不得悄悄少扫一层** —— 少扫的那层会被判成「未上传」，属于谎报。
2. **「列不出目录」≠「云端确实没有」**：前者（`_UNKNOWN`）沿用上次结论或判「待处理」并写明原因；后者（`None`）才判「缺失」。这两者混同会导致无意义的重复上传或漏报。
3. **快照模式仍然遵守「源未变 + 上次已同步 → 零网络请求」**：本版只是让它*更快*，不是让它*更激进*。
4. **自适应分页绝不会漏条目**：页码只按实际返回条数推进（见 ⑤），服务端夹 `per_page` 时自动退回普通翻页。
5. **并发与单线程行为一致**：`map_concurrent` 在 `workers=1` 时走的单线程分支，**异常同样装进结果**，与并发路径完全一致。
6. **HTTP 接口路径与请求/响应字段全部未改**，只**新增**了 `scanConcurrency` 一个配置项；前端与旧接口完全兼容。
7. **绝不删除任何文件**。云端多余的、本地多余的，一律只展示、不动手。
8. **凭据只存 StaticHash，不存明文密码**；token 用**裸值**放 `Authorization` 头（不加 `Bearer`），这是 OpenList 的约定。
9. **不暴露 TCP 端口**，只走统一网关 unix socket。
10. **`manifest` 里 `appname` 与 `desktop_applaunchname` 未动**，保证覆盖升级而不是并存。
11. **队列 / 绑定 / 配置的磁盘文件与 JSON 结构向后兼容**：旧数据可直接读入。

## 5. 已知边界与本次未做的事

1. **提速幅度是按请求数推算的，不是真机实测**。本版未在真实的大库（几万文件 / 几百目录）上做过计时对比。原理上：请求数与进程创建数被实打实砍掉（这一点有测试与代码可查），但实际墙钟时间还取决于你的网络延迟与存储负载。
2. **并发数不是越高越好**。默认 8 是「内网 OpenList」的稳妥值。如果 OpenList 在远端、或它挂载的网盘有严格限流，开太高反而会触发限流、整体变慢 —— 这种场景请把「扫描并发数」调小（2~4）。
3. **任务列表查询失败时仍无法自动补救**。此时状态保持原样，靠界面轮询等下一轮；如果 OpenList 长期不可用，超过 30 分钟才会判失败。这是刻意的保守策略——宁可不结论，也不谎报成功。（本版**未**对任务列表做缓存：2 秒轮询本来就长于任何有意义的缓存窗口，加了只会把「任务消失 → 判缺失」的转换**延后**，是净负债。）
4. **跨存储复制的最终一致性窗口**。"任务报告成功但云端暂时读不到文件"时不会立刻判失败，会给一段时间（上限 30 分钟）等它出现。
5. **"镜像同步"与"移动"仍未实现**（2.8.4 已下线相关入口）。要做成"删除云端多余文件"必须先把删除的确认流程、白名单、干跑预览做出来——属于新功能，不在本版范围。
6. **上传只做大小校验，不做哈希校验**。OpenList 的 `hash_info` 依赖具体存储驱动，不可靠。
7. **前端未做 i18n**，仍为简体中文。

六条经验，写在这里免得下次再踩：

- **改 `bindings.py` 的判定逻辑时，`tests/test_bindings.py` 里的假客户端要跟着改签名**，否则会以 `TypeError` 的形式炸出一片红。
- **测试用的假客户端 `stat()` 要能从云端树推导结果**，不能只认显式配置的表——否则快照模式下的 `stat` 永远返回"不存在"，测试会给出错误结论。
- **假客户端 `list_all()` 必须把显式配置的 `stats` 也合并进目录列表**：本版把绑定核对改成了「按父目录批量列」，若测试桩的 `stats` 与 `list_all` 两个数据源不一致，就会出现"显式配置了云端文件、批量查却查不到"的假阴性，把正确的代码判成错。（本轮 `test_task_succeeded_and_cloud_ok_marks_uploaded` 就是这么红过一次的。）
- **「刚从任务列表里消失」不等于「可以下结论」**：任务 id 与任务列表不同源、或轮询窗口错开时，一瞬间查不到是正常的。任何"查不到就立刻判失败/判缺失"的写法都会把正在进行的复制判死（本轮用户 bug 的根因）。判定必须走宽限期（`QUEUED_STALE_SECONDS`）。
- **本机 Windows 环境的 `os.symlink` 会静默降级成普通空文件**（不抛异常、`islink` 返回 False）。所以涉及符号链接的用例要**二次 `skipTest`** 兜住；真机是 Linux，那条路径是真跑的。
- **查询参数经 `parse_qs` 解析后值是数组**，`(query or {}).get("id")` 拿到的是 `["bd_xxx"]`。全项目都用 `_arg(query, "id")` 取首值，只有 `/api/bindings/progress` 漏了 —— 后果是它恒定返回 `progress: null`，而**这种失败是静默的**（前端 `catch` 一吞就什么都没发生）。端到端冒烟里补了「真 HTTP 按 id 命中」的断言，这类问题以后跑一次冒烟就会暴露。
- **要断言"请求还没返回时"的界面，就把请求挂住，不要用 sleep 猜**。本轮前端测试给假后端加了 `heldPaths`：命中就把响应挂在一个待释放的 Promise 上，测试同步地断言按钮已禁用、状态条已出现，再手动放行。并发/时序敏感的场景，用 Event 或挂起比 sleep 稳得多。

## 8. 结论

- 2.8.5 定位并消除的 **7 处性能放大源**本版完整承接，其中收益最大的三条是：**云端扫描同层并发**（①）、**绑定比对按父目录批量查**（②，1 万次请求 → 个位数）、**自适应分页**（⑤，大目录 8 次 → 2 次往返）。
- **本版主线**是给「一键上传」的提交提速（根因见 2.7）。「感觉是软件慢」这个直觉是对的：提交 120 个文件时**复制本身只占 30 次请求，另外 126 次全是软件自己的开销** —— 对同一批云端目录逐级查询、8 路并发之间又不共享结果、提交期间传输列表还在同步轰炸云端。现在一次提交内共享目录缓存，日常场景 **120 次 → 66 次（−45%）**，重复请求归零。
- 2.8.8 的交互优化（**点下去立刻有反应、过程可见、进行中不能重复点**，并把提交从串行改成并发）与那个**一直存在且完全静默**的接口缺陷修复（`/api/bindings/progress` 因查询参数没取首值而恒定返回 `progress:null`，前端那个「云端复制进度」轮询其实从未生效过）同样包含在本版。
- 2.8.7 的修复（绑定任务传完就从传输列表消失）与 2.8.6 的修复（一键上传毫无反应、传输列表里也不出现）同样包含在本版：前者让刚完成的任务以「已完成」留在列表里并能挑选查看，后者统一了 30 分钟宽限期、并修掉三处让 bug 表现为「静默」的前端/接口问题。
- 测试规模：2.8.4 的 482 项 → 2.8.5 的 528 项 → 2.8.6 的 534 项 → 2.8.7 的 538 项 → 2.8.8 的 572 项 → 本版的 **580 项**（Python 243→270→276→280→291→**299**，前端 239→258→258→258→281→**281**），端到端冒烟 36→37→37→40→**40** 项。本版新增 **8 项**，专钉这次的**请求数**：目录已存在时每个目录只查一次（不是「目录数 × 路径深度」）/ 总请求数接近目录组数 / 并发不重复创建同一目录 / 兄弟目录共享父级查询 / 缓存短路第二次调用 / 路径被同名文件占住仍报错 / 不传缓存也照常工作 / 提交进行中不去打云端。
- **未修改任何 HTTP 接口契约、磁盘数据结构、`.fpk` 权限位与应用标识**（`GET /api/bindings/progress` 新增可选参数 `submit=1`，`POST /api/bindings/upload` 的响应**新增** `submit` 字段，旧前端忽略即可），**也没有新增配置项** —— 提交并发复用已有的「扫描并发数」；**覆盖升级不会丢配置**。
- 刻意保留的保守语义（扫描失败必须报错、列不出目录 ≠ 云端没有、不可靠时不下结论、绝不删除文件）都在第 4 节逐条写明并有测试钉住，避免被后续修改当成 bug"顺手优化"掉。
