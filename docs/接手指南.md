## 1. 这个应用是干什么的

一句话：**在飞牛 fnOS 上，把 OpenList（NAS 里的网盘聚合器）挂载的本地目录，增量备份/同步到 OpenList 挂载的各个云端网盘（豆包、阿里、百度、天翼等）。**

核心卖点：
- **不下载文件到 NAS 本地**，而是调用 OpenList 的**服务端复制**（`POST /api/fs/copy`），让 OpenList 自己在两个存储之间搬运，NAS CPU/带宽零占用。
- **同步备份**：建一组"本地源目录 → 多个云端目标目录"的绑定，自动扫描本地有而云端没有的文件，一键/自动复制过去。
- **文件对比**：手动选两个目录（OpenList 上的路径），双向比对差异。
- **传输列表**：把上传、下载、OpenList 复制任务统一在一页显示。

## 2. 技术栈

| 层 | 技术 |
|---|---|
| 后端 | Python 3，**纯标准库**（无 pip 依赖），因为飞牛 fnOS 的 Python 是裁剪版，没有 pip |
| 前端 | 单个 `index.html`（HTML+CSS+JS 全内联，**没有构建步骤**，改完即生效） |
| 进程模型 | 单进程 + 后台线程（扫描线程池、上传队列 worker、自动扫描定时器） |
| IPC | 飞牛统一网关 Unix Socket（生产）；开发时可 `--tcp 127.0.0.1:8380` 直连 |
| 持久化 | JSON 文件（配置、绑定、队列状态），存在应用数据目录 |

## 5. 关键数据流

### 5.1 同步备份扫描 → 上传

```
用户点「扫描」或定时器到点
  → POST /api/bindings/scan
  → can_scan() 闸门：该绑定是否正在扫描/有上传任务进行中？
      ├─ 是 → 返回错误（"该同步有上传任务进行中..."）
      └─ 否 → start_scan()
          → _scan_worker 后台线程
              → 用全局扫描信号量限流（默认并发 2）
              → scan_cloud() 递归列源目录
              → 对每个目标列云端目录
              → verify.py 比对：找本地有、云端没有的文件
              → 结果写入 binding.files[].targets[].status
              → 若开了自动上传 → upload_to_targets()
                  → openlist.copy()（OpenList 服务端复制）
                  → 任务提交给 OpenList，前端通过 /api/openlist/tasks 轮询状态
```

### 5.2 传输列表

传输列表**不自己维护状态**，而是直接聚合三类来源：

| 来源 | 谁产生 | 前端怎么认 |
|---|---|---|
| 上传 / 下载队列任务 | `upload_queue.py` / `download_queue.py` | 常规行：进度条 + 取消/重传/删除 |
| OpenList 后台任务 | `GET /api/openlist/tasks`（`copy` 类型，id 前缀 `ol_`） | `isOpenList:true`：不画百分比，给取消/重试/删除 |
| **传输记录** | `transfer_records.py`（本地复制 `lc_` / 同存储云端复制 `olc_`） | `isRecord:true`：只画「源 → 目标」+ 删除 |

- `GET /api/openlist/tasks` 调 OpenList 的 `/api/task/copy/undone` + `/api/task/copy/done`
- `GET /api/upload/list` 把上传队列 + 下载队列 + 传输记录合成一个 `tasks`
- 前端把三者合并、排序（uploading > failed > pending > done）

**传输列表的按钮背后到底做了什么（v2.15.40 修正，别退回去）：**

| 按钮 | 后端 | 关键动作 |
|---|---|---|
| 全部暂停 | `/api/upload/pause` | **只设本地队列的 `_paused`**。OpenList 没有暂停概念，**绝不**顺手取消它的任务（旧实现这么干，导致"恢复后文件少了一批"） |
| 全部取消 | `/api/upload/cancel_all` | 本地两条队列 `cancel_all()`（并**解除暂停**）→ 对 `VISIBLE_TASK_TYPES`（当前只有 copy）逐个：拉 undone → `cancel_some` → **回读 undone 核验** → 残留逐条 `cancel?tid=` → 再回读。返回 `openlistRequested / openlistCancelled / openlistRemaining`，残留如实上报。**只取消列表里看得见的类型**，不动 `upload`/`move`（用户看不到它们） |
| 全部重试 | `/api/upload/retry {all:true}` | 本地 `retry_all()` ×2 **+** 对 `VISIBLE_TASK_TYPES`（当前只有 copy）调 `retry_failed`，条数用「调用前后 done 里失败数之差」核算；数不出来就返回 `openlistRetriedKnown:false`，**不许编数字** |
| 清除已结束 | `/api/upload/clear` | 本地 `clear_done()` ×2 + 传输记录 `clear_terminal()` + OpenList `clear_done`（copy 类型） |

### 5.3 OpenList 复制任务的 progress

**重要事实：OpenList 的 copy 任务返回的 `progress`、`size`、`uploaded` 全是 0。**
前端对这类任务（`isOpenList=true && size==0`）不显示百分比进度条，而是显示无限循环动画 + "复制中…"。
**不要**尝试乘 2 或猜进度——做不到。

### 5.4 两条"同步完成"的复制链路（BUG-3 的根因）

| 链路 | 实现 | 有没有任务 |
|---|---|---|
| 本地 → 本地 | `http_api._copy_local()`（`shutil`） | **没有** |
| 云端 → 云端**同存储** | `openlist.copy()`，服务端同步完成 | **没有**（响应里 `tasks` 为空） |
| 云端 → 云端**跨存储** | 同上 | 有（服务端建后台任务） |

前两种以前在传输列表里**什么都看不到**，用户点了复制以为没干活。现在由
`transfer_records.py` 落一条回执（有界 500 条 + `transfer_records.json` 落盘），
并在 `/api/upload/list` 里以 `isRecord:true` 合并进去。**新增复制链路时别忘了落记录。**

## 6. 历史踩过的坑（别再踩）

| 坑 | 真相 | 正确做法 |
|---|---|---|
| CSS 按钮过长 | ID 选择器（如 `#bindDlg .frow label`）优先级高于类选择器 `.frow label.switch`，后写的样式不生效 | 覆盖时用同等级 ID 选择器 |
| 传输列表 48-50 变动 | OpenList copy 任务不返回 progress，前端显示的是本地队列任务的进度 | copy 任务不画进度条，显示循环动画 |
| 卸载向导报错 | `wizard/uninstall.json`（带后缀）是错的，正确是 `wizard/uninstall`（无后缀，JSON 数组格式） | 用无后缀文件 |
| 文件夹折叠混乱 | 子文件夹本身也是 `.bf-folder`，折叠时遇到它就停止移除，导致只删直接文件 | 每个文件夹用 `.bf-children` 容器包裹所有子节点，折叠时整体移除 |
| JS `continue` 在 forEach 回调里 | forEach 回调不是循环体，`continue` 直接语法错误，整个页面 JS 崩溃白屏 | 用 `return` 代替 |
| 配置元素 id 改名后旧代码还引用 | JS 执行到不存在的 id 报错中断，后续初始化全没跑（表现为"文件夹不显示、提示未连接"） | 全局搜旧 id，一处不留 |
| http 日志刷屏 | 前端轮询 `/api/log` 自己的 GET 请求被记成日志，无限自引用 | 后端日志过滤 `/api/log` 请求 + 所有 GET 2xx 成功响应 |
| query.get("level") 返回列表 | 过滤参数可能是 `["error"]`，调 `.lower()` 崩溃 | `str(query.get("level") or "").lower()` |
| 多绑定同时到点扫描挤爆 OpenList | 所有绑定定时器同一时间触发，并发扫描 | 全局扫描信号量限流（默认 2 并发） |
| 上传中点扫描导致重复上传 | 扫描把正在复制的文件判成缺失，自动上传再次提交同一批 | v2.15.39 加 can_scan() 闸门，上传中禁止扫描 |
| OpenList 任务认领 | `/api/fs/copy` 响应的 tasks 数组数量必须等于本次提交的文件名数量，对不上说明混了别人的任务 | 数量不匹配就不认领 |
| **批量任务接口"HTTP 200 = 成功"** | OpenList 的 `cancel_some` / `delete_some` **无论 tid 是否存在都返回 HTTP 200 + code 200**，每个 tid 的结果在响应 `data` 里（`{tid: "task not found"}`，成功是 `null`）。旧代码只要不抛异常就 `return len(tids)`，于是"一个都没取消"也报"已取消 N 个" —— 「全部取消不生效」的真正根因 | 必须解析 `data` 逐条核实；`data` 为 `null`/`{}` 时承认"不知道"；失败 tid 逐条兜底，最后回读 `undone` 定论 |
| 只按错的类型去取消 | OpenList 的任务端点是 `/api/task/<type>/<action>`，类型取错就一个都取消不到 | 类型清单收敛在 `http_api.VISIBLE_TASK_TYPES`，**必须等于传输列表实际聚合的类型** |
| **取消/重试范围 ≠ 列表可见范围** | 「所见即所取消」：库里有 `upload`/`move` 类型任务，但 `h_openlist_tasks` 只聚合 `copy`。若「全部取消」按 `openlist.TASK_TYPES` 全量去扫，就会停掉用户**屏幕上从没出现过**的任务（含别的应用/别的用户建的）—— 那不是"取消全部"，是越界 | `VISIBLE_TASK_TYPES = ("copy",)`，`_cancel_openlist_undone` 与 `_retry_openlist_failed` 都用它。⚠️ 等列表扩类型（R05）时，**聚合范围与这个常量必须一起改**，只改一边等于把这条坑重新挖开。单条接口 `split_openlist_task_id` 仍用全量 `TASK_TYPES`（多试一个类型只会更准） |
| 暂停顺手取消 OpenList 任务 | 暂停变成不可逆：恢复后那些任务已经没了，用户看到"文件少了一批"。用户明确要求暂停**只对本地队列生效** | `h_upload_pause` 只设 `_paused`，前端文案说明 OpenList 不支持暂停 |
| 取消全部后仍处于暂停态 | `cancel_all()` 不解 `_paused`，用户取消完点「重试」什么都不会发生（worker 不取任务），看起来像"队列死了" | `cancel_all()` 里一并 `_paused.clear()` + `_wake_workers()` |
| **同步复制在传输列表里没有痕迹** | 本地→本地（`shutil`）与云端→云端**同存储**复制都是同步完成、**不产生任何任务**；`/api/upload/list` 只合并队列，于是列表一片空白 | 落 `transfer_records`（`lc_` / `olc_`），`isRecord:true` 合并进列表；前端走单独渲染分支（不画进度条、不给重试） |
| 传输记录被"参数错误"灌满 | 预检失败（源不存在 / 源即目标 / 目标是源子目录 / 越界 / 存储根目录）若也落记录，反复误操作会迅速填满 500 条上限，把真正的成功回执挤掉 | 预检类失败**只写日志**（原因已经通过响应里的 `failed` 逐条回给前端）；只有进入复制阶段后的成败才落记录 |
| OpenList 任务进度条冻住 | 刷新指纹 `queueSig` 只取 `uploaded`，而 OpenList 任务的 `uploaded` 恒为 0、进度在 `progress`（0-100）。`total_bytes>0` 的任务走百分比分支，于是画一次就再也不动 | 指纹里必须含 `t.progress` 与 `t.size`。**不要**改成"OpenList 一律 indeterminate"，那会丢掉真实百分比 |
| OpenList 任务 id 为空 | `"ol_" + ""` 让多个任务塌成同一个 `ol_`，前端按 id 去重后这些行**静默消失**；单条接口拿到 `ol_` 也定位不到任务 | `h_openlist_tasks` 跳过无 id 的任务并打一条汇总日志（每 2 秒一轮，别逐条打） |
| "全部重试"按钮出现了却没用 | 按钮显示条件算的是本地+OpenList 合并的失败数，但点击只重试本地队列 → OpenList 有失败项时按钮可见、点了什么都没发生 | `/api/upload/retry {all:true}` 里同时调 `retry_failed`（**只作用于 `VISIBLE_TASK_TYPES`，当前仅 copy**），分项回报 |
| **取消后回读只看 undone** | 任务离开 `undone` 有两种结局：被取消（state=4）或这期间自己跑完（state=2 成功 / 7 失败）。旧口径 `cancelled = requested - len(undone)` 会把后者也算成"已停下" —— 与"批量接口 200 就算成功"是同一类谎报 | `_task_buckets()` 同时读 undone + done：只认 done 里 state=4 为「已取消」，2/7 单列 `finished`，前端 toast 说「另有 N 个刚好完成」；独立假服务端回归钉死这条 |
| `retry_failed` 想报条数 | 该接口**不返回重试条数** | 调用前后各数一次 `done` 里 state∈(5,6,7) 的条数做差；拿不到就返回 `None`，前端如实说"无法核实" |

## 7. 配置项速查（config.py）

| 配置键 | 默认 | 说明 |
|---|---|---|
| `openlistUrl` | `http://192.168.0.10:5244` | OpenList 地址 |
| `openlistUser` | `ffvz` | 用户名 |
| `localRoot` | `/vol3/1000` | 本地根路径（面包屑会去掉这层前缀） |
| `autoScan` | `true` | 是否启用自动扫描 |
| `fullScanIntervalDays` | `7` | 全量扫描间隔天数（1-30） |
| `scanScheduleTime` | `03:00` | 全量扫描执行时间点 |
| `scanConcurrency` | `2` | 全局扫描并发数（1-10） |

冲突策略（绑定级）：
- `skip`（默认）：跳过已存在文件
- `overwrite`：覆盖
- `abort`：中止
